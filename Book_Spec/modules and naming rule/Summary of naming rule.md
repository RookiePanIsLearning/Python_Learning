
### 1. Python 物件命名規範總表

這張表定義了各類物件在「外觀」上應該長什麼樣子（基於 PEP 8）：

| **物件類型**          | **命名風格**             | **範例**           | **說明**             |
| ----------------- | -------------------- | ---------------- | ------------------ |
| **模組 (Module)**   | 小寫蛇形 (`snake_case`)  | `data_loader.py` | 盡量簡短，對應實體檔案。       |
| **套件 (Package)**  | 全小寫                  | `utils`, `api`   | 資料夾名稱，**不建議**使用底線。 |
| **類別 (Class)**    | 帕斯卡拼寫 (`PascalCase`) | `UserAccount`    | 每個單字首字母大寫，不加底線。    |
| **函數 (Function)** | 小寫蛇形 (`snake_case`)  | `get_user_id()`  | 通常以「動詞」開頭。         |
| **方法 (Method)**   | 小寫蛇形 (`snake_case`)  | `self.update()`  | 類別內部的函數。           |
| **變數 (Variable)** | 小寫蛇形 (`snake_case`)  | `retry_count`    | 具描述性的名詞。           |
| **常量 (Constant)** | 全大寫蛇形 (`UPPER_CASE`) | `API_TIMEOUT`    | 定義後不應修改的值。         |

### 2. 特殊底線之「密碼」含義

這張表解釋了當底線出現在不同位置時，在 Python 文化中所代表的「潛規則」：

|**語法格式**|**專業名稱**|**代表含義**|**影響範圍**|
|---|---|---|---|
|**`_var`**|單底線開頭|**內部使用** (Internal)|告訴開發者「沒事別動」，`from ... import *` 時會被忽略。|
|**`__var`**|雙底線開頭|**名稱修飾** (Private)|避免子類別意外覆蓋。會自動改名為 `_類別名__變數名`。|
|**`__init__`**|雙底線開尾|**魔術方法** (Dunder)|Python 系統保留的勾子，**禁止自創**此格式名稱。|
|**`var_`**|單底線結尾|**避開關鍵字**|當你想用 `class` 或 `list` 當變數名時的標準變通作法。|
|**`_`**|單獨底線|**佔位符** (Dummy)|代表「我不在乎這個值」。常用於迴圈或解包。|

### 3. 常見原則與避坑指南

這張表總結了開發時的心理邏輯與絕對要避開的行為：

| **類型**   | **原則 / 作法**          | **為什麼要這樣做？ (來由)**                              |
| -------- | -------------------- | ---------------------------------------------- |
| **核心原則** | **顯性勝於隱性**           | 與其用縮寫 `d`，不如用 `days_count`，增加可讀性。              |
| **核心原則** | **成年人哲學**            | Python 不強制鎖死私有權限，靠底線約定來互相尊重。                   |
| **避免作法** | **名稱遮蔽 (Shadowing)** | 絕對不要命名為 `id` 或 `type`，這會蓋掉系統內建功能。              |
| **避免作法** | **神秘縮寫**             | `get_i_f_db()` 是壞習慣，請寫完整 `get_info_from_db()`。 |
| **避免作法** | **混合風格**             | 在同專案混合 `camelCase` 與 `snake_case` 是災難。         |

---

> **💡 小提醒：**
> 
> 只要記住一個大原則：**「大寫開頭的是類別，全大寫的是常量，其他通通小寫加底線」**。這樣你就能掌握 90% 的 Python 命名精髓了！
